This chapter presents the theoretical foundations required to understand the
routing system developed in this work. Section~\ref{sec:manet} introduces
Mobile Ad-hoc Networks and their defining characteristics. Section~\ref{sec:mac}

and positions the present contribution relative to it.

\section{Mobile Ad-hoc Networks}
\label{sec:manet}

\subsection{Definition and Characteristics}

A Mobile Ad-hoc Network (MANET) is a self-configuring wireless network
that operates without fixed infrastructure~\cite{conti2014mobile}. Each
device simultaneously serves as communication endpoint and packet router,
forming a self-organising mesh. When two nodes are not within direct
radio range, intermediate nodes relay packets hop by hop until data
reaches its destination.

The defining property of a MANET is topology dynamism: as nodes move,
wireless links appear and disappear on timescales ranging from seconds
to fractions of a second. Routing protocols must detect failures and
install new paths faster than the topology changes, without any central
coordinator to orchestrate the process.

\subsection{Key Challenges}

\textbf{Dynamic topology.} Node mobility causes continuous topology
changes. Routes valid at one moment may be invalid moments later as
nodes move beyond wireless range, requiring continuous route adaptation.

\textbf{Hidden terminal problem.} When nodes A and C are both within
range of B but cannot hear each other, simultaneous transmissions by A
and C collide at B without either sender detecting the collision.
Contention-based protocols such as CSMA/CA are inherently vulnerable to
this problem; TDMA eliminates it by design.

\textbf{Resource constraints.} Battery-powered mobile nodes face energy
limitations. Routing protocols must minimise control traffic overhead
while maintaining route quality.

\subsection{Applications}

MANETs are essential wherever traditional network infrastructure is
unavailable or has been destroyed. Search and rescue missions in disaster
zones, military tactical communications in hostile environments, and
coordinated teams of autonomous robots in inspection or surveillance
scenarios all depend on this capability. The present work targets
precisely this last context: a mobile robot that must stream video to a
remote base station across a multi-hop path formed dynamically by the
robots themselves.

\section{Medium Access Control: CSMA/CA and TDMA}
\label{sec:mac}

\subsection{CSMA/CA}

Carrier Sense Multiple Access with Collision Avoidance (CSMA/CA) is the
contention-based medium access protocol used by IEEE 802.11 (WiFi). A
node wishing to transmit first senses the channel; if the channel
appears idle, the node waits a random backoff interval before
transmitting. When two nodes select the same backoff, their packets
collide and must be retransmitted.

CSMA/CA provides no timing guarantees: under congestion, repeated
collisions can delay transmission arbitrarily. The hidden terminal
problem further reduces effective throughput. RA-TDMAs+ runs on top of
the CSMA/CA hardware layer, overlaying it with a TDMA schedule that
eliminates intra-team collisions while allowing CSMA/CA to handle
external interference from nodes outside the team.

\subsection{TDMA}

Time Division Multiple Access (TDMA) divides time into repeating frames.
Each frame contains $N$ slots, one per node. A node may transmit only
during its assigned slot, so no two nodes transmit simultaneously and
collisions are impossible by construction.

For $N$ nodes with slot duration $T_{slot}$, the frame duration is:

\begin{equation}
T_{frame} = N \times T_{slot}
\label{eq:frame-duration}
\end{equation}

A guard interval is inserted between consecutive slots to absorb residual
clock drift and propagation delay. In the implementation used in this
work, each slot is 50\,ms, the guard time is 5\,ms (leaving 45\,ms of
usable transmission time per slot), and the three-node frame lasts
150\,ms, as shown in Table~\ref{tab:tdma-frame}.

TDMA's bounded latency (at most one full frame per transmission
opportunity) and collision-free operation make it well suited to
real-time video streaming, which imposes strict constraints on jitter
and packet loss.

\section{RA-TDMAs+ Protocol and Framework}
\label{sec:ra-tdma}

\subsection{Protocol Family Overview}

RA-TDMAs+~\cite{oliveira2018clockless} is the result of combining two
complementary protocols:

\begin{itemize}
  \item \textbf{RA-TDMAs}~\cite{sousa2012ra}: provides clockless relative
    synchronisation for a line topology, enabling high-bandwidth
    streaming from a mobile transmitter to a base station through relay
    hops.
  \item \textbf{RA-TDMA+}: extends RA-TDMA to dynamic mesh networks by
    distributing a connectivity matrix among all nodes, giving every node
    a consistent view of the current network topology.
\end{itemize}

By combining the synchronisation mechanism of RA-TDMAs with the
topology-tracking mechanism of RA-TDMA+, RA-TDMAs+ achieves clockless
synchronisation on dynamic mesh networks without requiring GPS or any
global time reference.

\subsection{Synchronisation Mechanism}

Each node transmits a beacon at the beginning of its assigned slot.
The beacon carries the node's ID, the slot ID, and the offset of the
transmission relative to the start of the node's slot.

A receiving node $j$ observing a beacon from node $i$ calculates the
packet delay $\delta_k$ as the difference between the measured arrival
time and the time at which the packet would have arrived had there been
no synchronisation error:

\begin{equation}
\delta_k = (rx_k - \hat{rx}_k + T/2)_T - T/2
\label{eq:sync-delay}
\end{equation}

where $rx_k$ is the real reception time, $\hat{rx}_k$ is the expected
reception time derived from the known slot structure, and the modular
arithmetic keeps $\delta_k$ in the range $(-T/2, T/2)$.

At the end of each round, node $j$ computes a shift $\Delta$ from the
observed delays and advances the start of its own slot by $\Delta$,
bounded by $\Delta_{max}$ (at most 25\% of the slot duration), to reduce
future overlap. This iterative adjustment drives all slots toward a
consistent global timing without any external reference.

\subsection{Topology Tracking: MATRIX Protocol}

Each node maintains a connectivity matrix $M$ where $M_{ij} = 1$
indicates that node $i$ is currently receiving packets from node $j$,
and $M_{ij} = 0$ indicates no active link. At the start of each slot,
the node updates its own row to reflect which neighbours it has heard
in recent rounds, then broadcasts the entire matrix. Receiving nodes
update their copy of the matrix with the freshest information from each
row, identified by an age field that prevents old data from overwriting
newer entries.

This flooding-with-aggregation mechanism ensures that within a bounded
number of rounds every node obtains a consistent view of the full
network topology, even when not all pairs of nodes have a direct link.
The matrix is the information source from which both the spanning tree
and the routing table are derived.

\subsection{TDMA Implementation Framework}

The experimental TDMA framework developed by
Almeida~\cite{almeida2023synchronization} provided the basis for the
present work. The framework implements RA-TDMAs+ in user space and
exposes a modular architecture composed of a core TDMA module and a set
of optional plug-in modules.

\textbf{TDMA\_Core.} The core module controls channel access. It
contains four threads: a transmit thread (TX) that is active only during
the node's assigned slot and sleeps otherwise; a receive thread (RX)
that decapsulates incoming packets and places them in a receive queue;
an event-handler thread that processes control events from plug-in
modules; and a configuration thread that manages round parameters and
slot boundaries.

Application packets reach the framework through a TUN virtual interface
(\texttt{tun0}). The TX thread reads packets from the TUN device,
prepends a TDMA header containing the packet type, a sequence number,
the relative transmission timestamp, and the slot boundaries, and
dispatches the encapsulated packet via a UDP socket over the physical
Wi-Fi interface (\texttt{wlan0}). On reception, the TDMA header is
stripped and the payload is returned to the \texttt{tun0} interface for
delivery to the application.

\textbf{Topology-Tracking Module (matrix.c).} This module implements
the MATRIX protocol described above. It maintains the connectivity
matrix as a packed C structure (\texttt{tdma\_matrix\_t}) containing
the matrix entries, the list of active node IDs, and per-row age
counters. At the start of each slot the module removes stale rows (age
above threshold), updates the local row, serialises the matrix, and
broadcasts it. It also computes a Minimum Spanning Tree (MST) from the
current matrix using Prim's algorithm and stores the result in shared
memory for use by the synchroniser and by any routing layer.

\textbf{Synchroniser Module.} The synchroniser wakes up three
milliseconds before the end of each round, reads the per-slot delay
values accumulated by TDMA\_Core, filters them through the MST to
exclude topological loops, computes the shift $\Delta$ per
Equation~\ref{eq:sync-delay}, and sends the result to TDMA\_Core as an
event. TDMA\_Core applies the shift before the next slot begins.

Inter-module communication uses two mechanisms: AF\_UNIX local sockets
for event messages between modules and TDMA\_Core, and POSIX shared
memory for the connectivity matrix, the spanning tree, and the delay
arrays that must be accessible by multiple modules with low latency.

\section{Routing Protocols for MANETs}
\label{sec:routing}

\subsection{Classification}

Topology-based routing protocols for MANETs fall into two main
categories.

\textbf{Proactive (table-driven) protocols} maintain routing tables for
all known destinations at all times, updating them through periodic
exchanges. Routes are immediately available when packets need to be
forwarded, at the cost of continuous control traffic overhead even when
no data flows. DSDV and OLSR are representative examples.

\textbf{Reactive (on-demand) protocols} discover routes only when
traffic must be sent, eliminating periodic overhead but introducing
route discovery latency before the first packet of each flow can be
forwarded. AODV and DSR are representative examples.

\subsection{Destination-Sequenced Distance Vector (DSDV)}

DSDV is a proactive protocol derived from the Bellman-Ford distance
vector algorithm~\cite{conti2014mobile}. Each node maintains a routing
table listing every known destination, the number of hops required to
reach it, and a sequence number that identifies the freshness of that
entry. Nodes periodically broadcast their tables to neighbours. When a
node receives an update, it compares sequence numbers: newer information
always wins, preventing routing loops.

Updates can be sent as full dumps (the entire table) or as incremental
carries (only entries that changed since the last dump), reducing
overhead during stable periods. If a node does not receive updates from
a neighbour for a configurable timeout, it marks the associated routes
as invalid and increments its own sequence number before rebroadcasting
the invalidation. DSDV's reliance on periodic broadcasts makes it
unsuitable for large or highly dynamic networks, but its table-driven
nature aligns naturally with RA-TDMAs+: the connectivity matrix already
provides fresh topology information at each slot boundary, so the
Bellman-Ford computation can be performed locally without additional
control traffic.

\subsection{Dynamic Source Routing (DSR)}

DSR is a reactive protocol that embeds the complete route in each
packet header. When a source needs to reach a destination for which it
has no cached route, it broadcasts a Route Request (RREQ) that
accumulates the path it traverses. The destination (or any intermediate
node with a valid cached route) replies with a Route Reply (RREP)
listing the full path back to the source. Intermediate nodes do not
maintain routing state; they simply read the next hop from the packet
header.

Route maintenance is handled by Route Error (RERR) messages: when a
node detects that a link it was using has failed, it notifies the source,
which removes the cached route and may initiate a new discovery. The
absence of per-node routing state reduces memory overhead but increases
packet header size and requires the source to have a consistent topology
view. In a TDMA network, route discovery must wait for each node's
designated transmission slot, which can introduce multi-round latency
before a route is established.

\subsection{Ad-hoc On-demand Distance Vector (AODV)}

AODV is also reactive and uses a similar RREQ/RREP/RERR mechanism to
DSR, but combines it with per-hop next-hop routing rather than source
routing. Each node stores only the next hop toward a destination rather
than the full path. Sequence numbers from DSDV are incorporated to
prevent stale route reuse and to ensure loop freedom.

Routes have an Active Route Timeout: unused entries are purged after a
configurable period, preventing the routing table from filling with
stale entries. When a link or node fails, AODV issues a RERR message
that propagates upstream along all active routes through the failed
link, triggering new discoveries in affected sources. The per-hop
storage model allows intermediate nodes to benefit from locally cached
routes and to correct routes using an updated topology view if topology
has changed while a packet was in transit.

\subsection{Optimised Link State Routing (OLSR)}

OLSR is a proactive link-state protocol optimised for dense ad-hoc
networks. Each node selects a subset of its one-hop neighbours as
Multipoint Relays (MPRs). Only MPRs forward control traffic, replacing
the network-wide flooding used by classic link-state protocols with a
targeted subset relay, substantially reducing control overhead.

Nodes exchange Hello messages to discover and maintain neighbour
relationships and to advertise MPR selections. MPRs generate Topology
Control (TC) messages that describe link-state information for their
MPR selectors. Each node accumulates TC messages and applies Dijkstra's
algorithm to build a complete routing table. Routes are recalculated
when a neighbour change or link expiry is detected. OLSR's Hello
messages serve the same neighbourhood discovery purpose as the
RA-TDMAs+ connectivity beacon, suggesting that the two mechanisms could
be unified to reduce overhead.

The conclusion drawn from this analysis is that a proactive, link-state
approach that reuses the topology information already disseminated by
the MATRIX protocol is the most natural fit. No route discovery phase
is needed: when the MATRIX beacon delivers an updated connectivity
matrix, the routing layer recomputes the MST and installs new routes
immediately, without waiting for additional protocol exchanges. The MST
is preferred over shortest-path routing because it maximises the use of
high-quality links and provides a loop-free tree structure that
simplifies next-hop derivation.

\subsection{Minimum Spanning Tree Routing}

A Minimum Spanning Tree (MST) of a weighted graph $G = (V, E, w)$ is
the subgraph $T \subseteq E$ that connects all vertices with minimum
total edge weight and contains no cycles:

\begin{equation}
\mathrm{MST}(G) = \underset{T \subseteq E}{\mathrm{argmin}} \sum_{(u,v) \in T} w(u,v)
\quad \text{subject to } T \text{ spans } V
\label{eq:mst-definition}
\end{equation}

When link weights reflect link quality (rather than hop count), the MST
naturally prefers higher-quality links. A node derives its routing table
from the MST by identifying the first hop on the tree path from itself
to each destination. If the link weight between nodes $i$ and $j$ is
defined as $100 - q_{ij}$, where $q_{ij} \in [0, 100]$ is a link
quality score, then minimising total weight is equivalent to maximising
the total quality of the spanning tree.

Prim's algorithm constructs the MST greedily: starting from a root
node, it repeatedly adds the minimum-weight edge that connects the
growing tree to an unvisited node. For $N$ nodes and a dense graph, the
time complexity is $O(N^2)$, which is negligible for the small networks
(3--10 nodes) targeted in this work.

\section{Related Work}
\label{sec:related-work}

\subsection{Layer 2 Routing in RA-TDMAs+}

Morais~\cite{morais2024synchronization} established the first routing
mechanism for RA-TDMAs+ networks, operating at the data link layer
(Layer 2) through ARP table manipulation on AlphaBot2-Pi robotic
platforms. Her work computed routes using Prim's MST algorithm applied
to the connectivity matrix distributed by the MATRIX beacon, and
achieved packet forwarding by rewriting destination MAC addresses at
each relay hop while leaving IP headers unchanged throughout the path.
This approach provided transparency to higher-layer protocols and was
successfully validated on physical robots, demonstrating the practical
feasibility of multi-hop video streaming in a robotic MANET.

The Layer 2 approach presented inherent observability limitations:
standard network diagnostic tools such as \texttt{traceroute} and
\texttt{ping} did not reflect the actual forwarding path, because
forwarding decisions occurred below the IP layer where those tools
operate. Integration with Linux networking features such as
\texttt{iptables} and \texttt{ip route} was similarly constrained.
The existing implementation also exhibited system-level instability
during operation, including runtime failures whose precise cause was
not fully identified. Additionally, the source code from that work was
not available for inspection or reuse; only the TDMA framework
developed by Almeida~\cite{almeida2023synchronization} was accessible.

These factors, taken together, motivated the construction of a new
routing system from the ground up on top of Almeida's TDMA codebase,
following Morais' thesis as a reference for the routing strategy but
adopting a Layer 3 architecture to address the observability and
stability limitations of the previous approach.

\subsection{Layer 3 Kernel Routing: This Work}

The routing mechanism developed in this dissertation operates at the
network layer (Layer 3) and integrates directly with the Linux kernel
routing subsystem. Rather than manipulating ARP tables, the system
programmatically installs routes into the kernel routing table via the
Netlink interface and derives forwarding decisions from an MST computed
over a weighted link quality graph. A dual routing table architecture
separates locally originated traffic (forwarded over the TDMA channel
via the TUN interface) from transit traffic (forwarded natively by the
kernel's IP forwarding engine via the physical Wi-Fi interface),
eliminating the need for any user-space forwarding plane.

The Layer 3 architecture provides full compatibility with standard IP
diagnostic tools, supports any IP-based application protocol without
modification, and relies entirely on production-quality kernel code for
packet forwarding. The design and implementation of this system are
described in Chapter~\ref{chap:implementation}.

\section{Summary}
\label{sec:background-summary}

This chapter introduced the concepts and prior work on which this
dissertation builds. MANETs require routing protocols capable of
adapting continuously to topology changes without central coordination.
TDMA, specifically RA-TDMAs+, provides collision-free medium access and
distributes topology information via periodic beacons, making a
proactive MST-based routing approach both natural and efficient. The
TDMA framework provided by Almeida served as the foundation for
implementation. The previous Layer 2 routing work by Morais proved the
feasibility of multi-hop communication in this context and provided the
MST routing strategy adopted here; the present work extended that
foundation by implementing routing at Layer 3 and integrating it with
the Linux kernel networking stack.
